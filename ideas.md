# Идеи приложений для Rome

Дата: 2026-11-06. Связанный план: [building.md](building.md).

Критерии отбора:
1. **Нет в экосистеме.** Сверял с rome.builders/apps (приложения Rome), галереей Arena и списком rome.builders/ideas.
2. **Нужно после TGE / в mainnet.** Продукт полезен на Rubicon независимо от аирдропа (токена пока нет, см. building.md §2).
3. **Использует фишку Rome.** Dual-lane, CPI в Solana, встроенный бридж. Без этого продукт мог бы жить где угодно, и Rome его не продвинет.
4. **Двигает Arena.** Реальные пользователи, транзакции и объём на Rubicon.
5. **Подходит под опыт.** RPC, Telegram-уведомления, аналитика (LitVM, rpc-litvm.pro).

## Часть 1. Разбор 7 идей ChatGPT

Общий совет ChatGPT («продукт, который приводит новых пользователей и разработчиков, а не фарм») верный. Чек-лист артефактов тоже верный, я перенёс его в building.md §5 и дополнил.

### 1. Rome Pulse (аналитика экосистемы): согласен, с изменениями

- **Пересечения:** в официальных идеях есть **Two-Sided Analytics** (потоки и позиции EVM- и Solana-кошельков в одних пулах). Civitas частично показывает активность по кошелькам. Via показывает отдельные транзакции, но **без API и без агрегатов**.
- **Почему нужно:** у Rome нет индексатора, сабграфов и публичного API эксплорера. Любой билдер, которому нужны метрики для Arena или гранта, сейчас вынужден писать свой сканер.
- **Что изменить:**
  - Главный срез — **EVM-lane vs Solana-lane**: сколько пользователей пришло с MetaMask, сколько с Solana-кошельков, сколько через бридж и из какой сети (CCTP). Это уникально для Rome, и именно это Rome хочет показывать миру.
  - Метрики по каждому приложению Arena: публичная страница «доказательства использования» (уникальные кошельки, tx, объём), которую билдер может приложить к заявке на грант.
  - TVL считать только там, где он реально есть (Portus/Kamino, вольты). Сейчас его почти нет, и пустой график TVL плохо выглядит.
  - Связь EVM-tx и Solana-tx через `rome_solanaTxForEvmTx`: какие Solana-программы реально вызываются через CPI (Kamino, Meteora, SPL).
- **Риск:** Rome может сделать Two-Sided Analytics сам. Решение: выйти быстрее и согласовать в Discord.
- **Вердикт:** делать, но как фронтенд к общему индексатору (см. идею A ниже).

### 2. Rome Watch (мониторинг и Telegram-алерты): согласен, сильнейшая по опыту

- **Пересечения:** официальная идея **Stalk In** (доступность эндпоинтов, исходы транзакций со ссылками на Solana). Партнёр **Guardrail** — это security-мониторинг для протоколов, а не уведомления для людей.
- **Почему нужно:** публичного мемпула нет, `debug_traceTransaction` нет, у Via нет подписок. Билдер не узнает, что его контракт падает, а пользователь — что пришёл перевод.
- **Что изменить и добавить:**
  - Rome-специфика, которой нет нигде: **алерт про упавшую транзакцию с расшифровкой причины** (CU limit, неподдерживаемый opcode, CPI depth, нехватка газа на создание аккаунта) и ссылкой на Solana-tx.
  - **Статус-страница сети:** RPC Hadrian и Rubicon, Bridge API, Oracle Gateway (свежесть `latestRoundData`), цена газа. Это прямо Stalk In.
  - Алерты на **цену газа** и на **неудачные бриджи** (CCTP завис).
  - Для билдеров: вебхук и TG-бот на события своего контракта без своего сервера.
  - Пример с Portus хороший: «крупный депозит в Portus», «изменился APY Kamino».
- **Монетизация:** бесплатно 1–3 подписки, дальше платная подписка в **USDC на Rubicon**. Это даёт и выручку, и on-chain транзакции для Arena.
- **Вердикт:** делать первым продуктом для людей. Быстро, сильная сторона пользователя, нужно сразу.

### 3. Rome Pay (платёжные ссылки): согласен, лучшая идея для рангов Arena

- **Пересечения:** официальная идея **USDC Payments**. Никто её не построил, а Rome её явно хочет.
- **Почему нужно после TGE:** газ на Rubicon — это USDC. Пользователь, у которого есть USDC в любой из 7 сетей CCTP или в Solana, может заплатить мерчанту. Мерчант получает USDC в одном месте и может сразу положить его в Portus/Kamino под процент. Такая связка есть только на Rome.
- **Что изменить и добавить:**
  - «Не мост, а платёжная оболочка» — верно. Но **встроенный бридж должен быть внутри чекаута**: плательщик с USDC на Base нажимает «Pay», а Rome Bridge (CCTP) делается под капотом.
  - Оплата и с MetaMask, и с **Solflare** (Solana v1). С Phantom Solana-lane пока не работает, это надо честно показать в UI.
  - Учесть, что **первый перевод на новый адрес стоит ~0.11–0.27 USDC**. Решение: контракт-эскроу/инвойс, который уже существует (платёж в существующий контракт дешёвый), и вывод мерчанту пачкой.
  - Вебхуки, QR, инвойсы, история — да. Плюс **«Claim Links»**: отправить USDC по ссылке человеку без кошелька Rome (он заходит, подключает любой кошелёк, забирает). Это вирусный способ привести новых пользователей.
  - Опционально: **авто-депозит выручки в Portus** (yield на остаток мерчанта через CPI в Kamino). Это ещё и TVL для рангов.
- **Вердикт:** делать. Главный продукт для Arena (пользователи + транзакции + объём).

### 4. Rome Dev Studio (браузерная IDE): частично согласен, сузить

- **Пересечения:** в списке идей Rome нет. Это реальный пробел.
- **Что не так:** браузерная IDE с Solidity playground — это переписывание Remix. Remix уже работает с Rome как с обычной EVM-сетью (RPC + chainId). Долго, дорого, ценность низкая.
- **Что оставить, потому что этого нет нигде:**
  - **CPI Simulator / Visualizer.** Перед отправкой транзакции вызвать `rome_emulateTx` и `rome_emulateCallAccounts`, показать дерево: EVM-вызов → какие Solana-программы → какие аккаунты, CU, хватит ли 1.4M CU, будет ли итеративный режим. Via показывает это только **после** транзакции.
  - **Газ-калькулятор.** «Сколько стоит операция в USDC на Rubicon», с учётом создания аккаунтов. Сейчас это главная непредсказуемость для билдеров и пользователей.
  - **Compatibility checker** для контрактов: SELFDESTRUCT, `transfer/send` с расчётом на stipend, modexp, лимит 256 слотов, глубина CPI. Можно в виде CLI/линтера + GitHub Action.
  - **Calldata/ABI-кодер для CPI** (Kamino, Meteora, SPL), на базе энкодеров из `rome-sdk-ts`.
- **Вердикт:** делать как **Rome Devtools** (simulator + gas + checker), а не как IDE. Это лучшая идея для гранта, потому что Rome нужны разработчики.

### 5. Rome Chain Economics (калькулятор своей цепочки): не согласен как с отдельным продуктом

- **Пересечения:** у Rome есть Sovereign Portal, App Sovereignty «Live with partners». Инфраструктуру поднимает команда Rome.
- **Почему не отдельным продуктом:** аудитория — единицы команд, и только на последнем шаге (Academy сама говорит, что своя цепочка — это не первый шаг). Нет пользователей, нет транзакций, Arena-ранги не двигает.
- **Что оставить:** модуль в Devtools или страницу-лендинг «Стоит ли тебе своя цепочка?»: комиссии в казну, газ-токен, глубина пула Meteora для цены газа, сравнение с общим Rubicon. Это хороший контент для поста в X, а не продукт.
- **Вердикт:** понизить до модуля или статьи.

### 6. Rome Activity (профили, квесты, NFT): не согласен, конфликт с Rome

- **Пересечения:** **Civitas** (Laurels по кошелькам) и Arena — это ровно оно, и это делает сама команда Rome. Ещё официальная идея Token Rewards.
- **Почему нет:** квесты и достижения привлекают фармеров, а не пользователей. Совет самого ChatGPT («не фарм») здесь противоречит идее. Конкурировать с официальным Civitas бессмысленно.
- **Что можно взять:** **квесты как B2B-инструмент для билдеров Arena** («пройди онбординг в моём приложении»), с проверкой через индексатор. Но это позже и только если Rome не сделает сам.
- **Вердикт:** не делать сейчас.

### 7. Rome API Hub (единый API): согласен с сутью, не с упаковкой

- **Пересечения:** `rome-registry` (факты о цепочках и токенах), `rome-sdk-ts` (отправка транзакций), Bridge API. Часть «балансы» сводится к обычному RPC.
- **Что реально нужно:** то, чего нет у RPC: **индексированные данные** (история транзакций по адресу без ограничения `eth_getLogs`, балансы EVM-адреса **и** связанного Solana-аккаунта, связь EVM-tx и Solana-tx, события с вебхуками).
- **Вердикт:** делать как **общий бэкенд** для Pulse, Watch, Pay (идея A). Внешний API с ключами и тарифами — побочный продукт этого бэкенда, а не отдельный проект.

## Часть 2. Мои идеи

### A. Rome Index: индексатор + GraphQL + вебхуки (фундамент)
- **Проблема:** Via без API, индексатора и сабграфов нет, блоки — это слоты Solana (~465M номер, почти все пустые), `eth_getLogs` ограничен. Каждый билдер пишет свой сканер.
- **Что:** подписка `eth_subscribe` (newHeads, logs) + бэкфилл, связка EVM-tx и Solana-tx через `rome_solanaTxForEvmTx`, декодирование событий ERC-20 / SPL_ERC20 обёрток / бриджа. GraphQL/REST, вебхуки.
- **Почему Rome:** первая инфраструктура такого рода в экосистеме; Rome нужна, чтобы привлекать разработчиков.
- **Монетизация:** бесплатно для билдеров Arena (рост и лояльность), платные тарифы для коммерческих.
- **Приоритет:** 1 (на нём стоят Watch, Pulse, Pay).

### B. Rome Devtools (из Dev Studio, см. выше)
- CPI Simulator (`rome_emulateTx`), газ-калькулятор в USDC, compatibility checker (CLI + GitHub Action), энкодер CPI-calldata.
- **Приоритет:** 3. Сильная заявка на грант.

### C. Rubicon-ready scaffold
- **Проблема:** `create-rome-app` и `rome-cli` закреплены на registry v0.2.0, где **нет Rubicon**. Новый билдер не может сразу сделать mainnet-приложение.
- **Что:** шаблон (или PR в `create-rome-app`) с registry v0.3.0+, проекцией registry в JSON для браузера, обоими lane, встроенным бриджем, правильной оценкой газа.
- **Лучше всего:** сделать **PR в официальный репо Rome**. Это мало работы, а заметность у команды максимальная.
- **Приоритет:** быстрая победа, сделать во время Фазы 1 (обучение).

### D. Rome Onboard: вход в Rome за один экран
- **Проблема:** новому пользователю нужно понять, что газ — это USDC, найти бридж, выбрать сеть, получить USDC на нужный адрес. Высокая стоимость первой операции пугает.
- **Что:** виджет «у тебя есть USDC на Base / Arbitrum / Solana → через 1 клик у тебя Rome-адрес с газом», с показом стоимости заранее. Встраиваемый в чужие приложения (iframe/React-компонент).
- **Пересечения:** официальные идеи Bridge Funding Interface и Token On-Ramp. Rome Bridge уже есть, но как отдельное приложение, а не встраиваемый компонент.
- **Приоритет:** 4, или как часть чекаута Pay (там это уже нужно).

### E. Rome Approvals: dual-lane Revoke + Wallet Dashboard
- **Проблема:** у Rome один и тот же пользователь может иметь EVM-адрес и производный адрес от Solana-кошелька. Где мои токены, кому я дал approve, что лежит в SPL-обёртках — непонятно.
- **Что:** список балансов (EVM + SPL обёртки), approvals с отзывом, история бриджей. Официальная идея **Wallet Dashboard**.
- **Почему:** маленький, полезный навсегда, быстро выходит в mainnet. Нужен индексатор (A) для approvals.
- **Приоритет:** быстрая победа для майлстоуна «Live on mainnet».

### F. Rome Treasury: мультисиг и казна для dual-lane команд
- **Проблема:** у команды часть подписантов на EVM-кошельках, часть на Solana. Обычный Safe не умеет принимать подписи от Solana-кошелька. Официальная идея Treasury Router близка.
- **Что:** мультисиг, где подписантами могут быть и MetaMask, и Solflare (через derived-адреса), с авто-размещением свободного USDC в Portus.
- **Риск:** много безопасности, нужен аудит. Делать позже, после доверия от Arena.
- **Приоритет:** 5 (позже).

### G. Arena Builder Kit
- **Проблема:** билдеру нужно показать прогресс в Arena: привязать контракты, собрать метрики, писать апдейты.
- **Что:** публичный бейдж/страница метрик приложения (на базе индексатора), генератор поста в X с цифрами, автоматическая проверка «что у тебя готово для следующего майлстоуна».
- **Риск:** зависит от того, откроет ли Rome API Arena. Сначала спросить в Discord.
- **Приоритет:** дополнение к Pulse.

**Решение (2026-11-06): первым делаем Rome Pay.** Регистрация в Arena через `?idea=USDC Payments`. Полный индексатор для старта не нужен: Pay слушает события только своего контракта (`eth_subscribe` logs). Этот listener потом станет ядром Watch и Index.

### Rome Pay — объём работ

**v1, MVP на Hadrian (до Built on testnet и заявки на грант):**
- Контракт `PayRouter` (готов, `pay/contracts`): некастодиальный. `pay(merchant, amount, ref)` переводит wUSDC от плательщика сразу мерчанту (минус комиссия ≤1%), событие `Paid`. Инвойсы живут off-chain (бэкенд), on-chain нет хранилища на каждый платёж: на Rome каждый новый слот может стоить нового Solana-аккаунта. Дедупликация по `ref` на бэкенде.
- Чем платить (решено по докам): **только ERC-20 wUSDC**, не `msg.value`. У Solana-пользователя на EVM-стороне есть только SPL-обёртка. Флоу: Solana — fund leg → `create_pda` (один раз) → `approve_spl` grant (один раз) → approve → pay. MetaMask — `withdraw_to_ata` (обернуть газ USDC в wUSDC) → grant (один раз) → approve → pay.
- Мерчанту нужен существующий wUSDC-аккаунт (иначе первый платёж стоит плательщику ~2.5M газа). Онбординг мерчанта: обернуть немного USDC.
- Страница оплаты `/pay/<id>`: MetaMask + Solflare, сумма, QR, заранее показанная стоимость газа (`eth_estimateGas`).
- Кабинет мерчанта: создать ссылку, список платежей, статус, экспорт CSV.
- Бэкенд: listener `InvoicePaid` → запись в БД → **вебхук** мерчанту (HMAC-подпись, ретраи) + опционально TG-уведомление.
- Метрики для Arena и гранта: платежи, уникальные плательщики EVM vs Solana.

**v2, перед mainnet:**
- Бридж внутри чекаута: плательщик с USDC на Base / Arbitrum / Solana (CCTP через `@rome-protocol/sdk/bridge`).
- **Claim Links**: отправить USDC по ссылке человеку без кошелька Rome.
- Аудит, перенос на Rubicon, проверка полного цикла с маленькими суммами.

**v3, после mainnet:**
- Авто-депозит выручки мерчанта в Portus/Kamino.
- Комиссия протокола (например 0.3–0.5%), API-ключи, SDK/виджет для встраивания.

Второе приложение в Arena: **Rome Watch** на базе того же listener'а.
